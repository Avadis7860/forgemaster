# dispatch-orchestrator — runbook (le cœur de la forge, Phase C : la boucle enchaîne dispatch → gate → merge-ready, feature-groupe-de-tasks)

`orchestrator.py` porte la boucle de forge de `forgemaster run <project>`. L'unité n'est pas la task mais la **feature** — un groupe de tasks séquentielles = une branche = un worktree = un **mutex** (un seul worker à la fois). La boucle draine la roadmap : elle découvre les features prêtes, en dispatche jusqu'à `max_parallel` en parallèle, avance le DAG intra-feature au fil des succès (task → `done`), puis finalise chaque feature au travail complet (Tier-0 + reviewer → merge-ready). Invariant cardinal : la boucle produit des commits et un verdict de gate, **jamais un merge** — le GO qui merge/détruit reste un gate humain fail-closed (`human_go=False` en dur).

## run_project() — draine la roadmap, boucle principale
`src/forgemaster/dispatch/orchestrator.py:223` · appelé par cli_dispatch (route `forgemaster run`) / le daemon
Entrées : `conn` (connexion principale, seule lectrice-assignatrice), `settings`, `project`, `max_parallel` (défaut 2), et les runners injectables (`git`, `runner`, `review_runner`). **Avant** la boucle : un auto-heal (`interview.reconcile_socle` clôt un socle déjà travaillé dont l'interview a été interrompue — sinon il resterait tenu et bloquerait l'aval), puis le **gate socle** — tant que le socle du projet n'est pas `merged` dans `dev`, les features de travail sont **tenues** (`held_for_socle` + alerte `socle_hold`, ce n'est PAS un échec) parce qu'elles brancheraient depuis un `dev` sans design ; le socle lui-même reste dispatchable. Comportement : sous un `ThreadPoolExecutor`, boucle infinie — à chaque tour elle teste d'abord la **sentinelle d'abort** (posée par le bouton UI / `forgemaster abort` / Ctrl-C) et cesse d'assigner si elle est levée (run `aborted`, rien mergé, re-runnable) ; sinon elle demande à `_discoverable_features()` les slugs dispatchables — **en excluant** ceux déjà rangés (`failed`, `needs_interview`, `held_for_socle`, `rate_limited`, `interrupted`), faute de quoi ils resteraient READY et la boucle spinnerait —, réserve chacun dans `in_flight` **avant** le `submit` (mutex par feature : jamais deux fois la même en vol), puis `wait(FIRST_COMPLETED)`. Pour chaque future terminée elle retire le slug d'`in_flight`, collecte le rapport, en émet l'alerte **pendant** le drain (`_emit_report_alert` — aucun blocage silencieux) et le range dans **une** disposition : `needs_terminal` → tenue pour `forgemaster interview` ; `rate_limited` → plafond 5 h org atteint, tenue et re-runnable (et l'assignation s'arrête là, les autres seraient rejetées de même) ; `interrupted` → SIGTERM externe, tenue mais le drain **continue** (l'interruption est par-worker, pas org-globale) ; `ok` faux → `failed`, exclue du reste du run. Sortie de boucle quand `pending` est vide (rien en vol ni à soumettre → drainé). Puis, drain fini, elle finalise chaque feature complète (`_worked_complete_features` → `finalize_feature`), range toutes les features non-inertes via `_dispositions` (une seule catégorie chacune, sans double-compte), résout les alertes worker-level de celles qui ont drainé, et rend le rapport agrégé de `_summarize`. Invariant de terminaison : chaque run fini fait progresser une task (`done`) OU exclut/tient sa feature → le travail restant décroît strictement. Le merge n'est PAS ici — la boucle s'arrête à merge-ready.

## _dispatch_one() — dispatche la NEXT task d'une feature, dans son thread
`src/forgemaster/dispatch/orchestrator.py:116` · appelé par run_project (via `pool.submit`, un thread par feature en vol)
Entrées : `settings`, `project`, `feature`, `git`, `runner`. Comportement : ouvre une **connexion propre au thread** (`store.connect`, `check_same_thread` — concurrence SQLite absorbée par le `busy_timeout` posé à la connexion), délègue à `worker.dispatch_next` sur `feature_ref = project/feature`. **La clôture `in_progress` → `done` ne lui appartient PAS** : elle est portée par le PRIMITIVE `dispatch_next` (`_on_success`), pour qu'un `forgemaster dispatch` en CLI seul avance sa task sans dépendre de la boucle. Cette fonction ne duplique plus la transition — elle traduit. Une disposition à connaître : un `GitOpError` levé par `worktree.reserve → rebase_onto` (base périmée non réalignable, un sibling a avancé `dev` sur des fichiers en conflit) est **attrapé** et rendu comme `needs_redrain=True` au lieu de remonter par `fut.result()` — le drain continue les autres features et l'humain reçoit un `forgemaster redrain <p>/<f>` actionnable. Sortie : rapport `{feature, task, ok, reason, needs_redrain, needs_terminal, rate_limited, interrupted}`, **jamais une exception** vers la boucle (un worker échoue, il ne plante pas) ; les trois derniers drapeaux portent respectivement la task interactive (→ interview), le plafond 5h org et le SIGTERM externe. Appelé exclusivement depuis les threads de `run_project`.

## _discoverable_features() — sélectionne et priorise les features dispatchables
`src/forgemaster/dispatch/orchestrator.py:90` · appelé par run_project (une fois par tour de boucle)
Read-only sur la connexion principale. Entrées : `conn`, `project`, `in_flight`, `failed`. Comportement : calcule une fois par passe le DAG **inter-feature** (`resolver.classify_features`, deps v10), puis pour chaque feature écarte celles qui sont inertes (`merged`/`cancelled`), en vol, en échec, ou dont l'état inter-feature est bloqué (`BLOCKED_DEPS`/`ERROR`/`CYCLE` — prérequis non `merged`, ou graphe malformé) ; charge l'index intra-feature (`index_for_feature`) et n'admet la feature que si `resolve_next` expose une NEXT task READY. Sortie : slugs triés par `(priorité, created_at, slug)` → les priorités hautes soumises d'abord. Invariant : une feature n'est dispatchable que si toutes ses prérequises sont `merged` (le cas design→code est enforcé, plus « résolu à la main par l'ordre de merge »).

## _worked_complete_features() — les features dont le travail est fini
`src/forgemaster/dispatch/orchestrator.py:147` · appelé par run_project (une fois, après le drain)
Read-only. Entrées : `conn`, `project`, `failed`. Comportement : retient les features encore `active` (ni `merged` ni `cancelled`), non en échec, dont **toutes** les tasks sont `done`/`cancelled` avec **au moins une** `done` (≥1 task réellement travaillée). Sortie : liste de slugs prêts à la finalisation (Tier-0 + review → merge-ready). Invariant : merge à feature **complète** — on ne finalise jamais une feature partielle. C'est la porte d'entrée du tronçon qualité de la boucle.

## finalize_feature() — Tier-0 + reviewer (+ Tier-1.5 et woaw auto) → verdict de gate en preview
`src/forgemaster/dispatch/orchestrator.py:163` · appelé par run_project et run_feature (une fois par feature complète)
Entrées : `conn`, `settings`, `project`, `feature`, `review_runner`. Comportement : résout la feature, calcule le **SHA de HEAD** de sa branche (`git.feature_sha`) et le diff vs `_BASE_BRANCH = "dev"` (fraîcheur liée au SHA — si la branche est absente, jamais dispatchée, retourne un blocker propre) ; si le worktree existe, exécute le **Tier-0 toolchain** (déterministe, SHA-bound) et écrit son verdict. Puis le **reviewer Tier-1** (charte : LLM génère / déterministe gate) — sauf s'il n'y a **aucun code à reviewer** (`has_reviewable_code` faux : docs-only ou diff vide), auquel cas Tier-1 est marqué N/A sans gaspiller un worker ; sans ce court-circuit, un diff vide ferait « reviewer skip → verdict absent → blocage circulaire ». Deux étages **automatiques** s'ajoutent quand le diff touche une surface UI (`verify.has_visual_change`) : le **Tier-1.5 feature-verified** (`verify.autoverify_feature`) si la preuve n'est pas fraîche pour ce SHA — best-effort mais **fail-CLOSED** (pas de preuve ⇒ le gate l'exige, jamais de faux-vert), et l'**axe woaw** (`woaw_dispatch.dispatch_woaw`), verdict esthétique **ADVISORY** lu en consultatif — il n'affecte ni `gate_green` ni le merge, et son échec ne casse jamais une finalisation. Le gate est enfin évalué en **preview `human_go=False`** — on ne merge JAMAIS ici. Cycle de vie de l'alerte `gate_red` (aucun blocage silencieux) : gate rouge → alerte actionnable portant les blockers ; gate redevenu vert → l'alerte ouverte est résolue. Sortie : `{feature, merge_ready, blockers, review}` où `merge_ready` reflète `gate_green`. Best-effort : une pièce en échec laisse le gate bloquer proprement et le blocker est surfacé. Invariant fail-closed : cette fonction est le mur entre l'autonomie (produire un verdict) et l'action destructrice (merge/destroy), qui exige le GO humain séparé (`forgemaster merge --go`).

## Zones non détaillées
- `_summarize` (`orchestrator.py:430`) — helper de formatage : agrège runs + finalisations en rapport (`dispatched`/`ok`/`failed`/`drained`/`merge_ready`) ; `drained ⟺ aucune feature en échec`. Pas de logique de boucle.
- `cli_dispatch` (`orchestrator.py:474`) — route CLI `forgemaster run <project> [--max-parallel N]` : **gate d'auth fail-closed** (refuse avant tout spawn si pas d'auth Claude explicite, exit 2), appelle `run_project`, imprime le rapport et les lignes merge-ready (`✅` avec la commande `forgemaster merge … --go`, `🟡` sinon). Exit 0 si drainée sans échec, 1 sinon.
