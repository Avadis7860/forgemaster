# dispatch-worker — runbook (spawn du worker claude headless + reviewer Tier-1 : prompt, parse du résultat, findings)

La forge lance deux agents `claude -p` **headless** en local, dans le worktree de la feature, transport (`runner`) toujours injectable (les tests ne spawnent jamais un vrai `claude`). Le **worker** GÉNÈRE (allowlist code, `acceptEdits`) sur la NEXT task ; le **reviewer** GATE (read-only, `work=False`) le diff `dev...branche`. Les deux partagent le même builder d'argv et le même parseur de sortie : l'argv fixe `--output-format`, `--session-id`, l'allowlist et le DENY destructif ; le prompt part **sur stdin** (parade E2BIG), jamais dans l'argv. La sortie `stream-json` (NDJSON) est normalisée en un dict `{ok, is_error, result, …}` fail-loud, dont on tire soit le minerai décision, soit les findings du verdict.

## build_headless_argv() — argv de `claude -p` (partagé worker + reviewer)
`src/forgemaster/dispatch/worker.py:107` · appelé par `dispatch_next()` et `dispatch_reviewer()`
Construit la liste d'argv PURE : `claude -p --output-format <fmt> --session-id <id>`. Si `output_format == "stream-json"` ajoute `--verbose` (exigé par `claude` pour ce format). `work=True` → allowlist de code (`WRITE_CODE_TOOLS`) + `--permission-mode acceptEdits` (sans lui `claude -p` refuse Write/Edit) ; `work=False` → allowlist read-only (`READONLY_TOOLS`) + `--permission-mode dontAsk`. **`--permission-mode` est posé dans TOUS les cas** et c'est load-bearing : sans lui, un outil hors allowlist ne se refuse pas, il **prompte** — donc en headless il HANG jusqu'au timeout. `allowed_tools`, s'il est fourni, **override** ce choix : c'est ainsi que le reviewer injecte son allowlist read-only *élargie* (`reviewer.REVIEW_TOOLS` : git en lecture + les maps), ce qui a mis fin à son spin sur `Bash`. Le DENY destructif (`rm`/`git push`/`git reset`/`sudo`) est posé **dans tous les cas** et **prime** sur l'allow (précédence deny > ask > allow). `mcp_config` fourni → `--mcp-config <f>` (non-strict). Le prompt n'est JAMAIS dans l'argv. Invariant : `work` sépare génère (worker) de gate (reviewer, read-only).

## dispatch_next() — spawn du worker sur la NEXT task de la feature
`src/forgemaster/dispatch/worker.py:187` · appelé par `cli_dispatch` (route `forgemaster dispatch <feature>`) et l'orchestrateur
Entrées : `conn`, `settings`, `feature_ref="projet/feature"`, `git`/`runner` injectables. **Trois refus de spawn, pas un.** (1) *no-task-no-dispatch* : aucune task ou aucune task READY (`resolver.resolve_next`) → `{dispatched:False, reason}`. (2) *fork headless↔interactif* (v12) : une task `mode="interactive"` (interview, cadrage) ne peut pas se mener en `claude -p` — un headless n'interviewe personne. Le refus est posé **avant** tout `reserve`, la task reste `todo` (jamais `in_progress`, jamais un faux-`done`), et `needs_terminal=True` est SURFACÉ pour que l'humain la mène par `forgemaster interview <projet>`. Le branchement appartient au dispatch, pas au worker. (3) le preflight ci-dessous.
Sinon : réserve worktree+port (`worktree.reserve`), compose le prompt (`build_worker_prompt`), résout le **modèle de la facette** (`facet.resolve_facet_model` — le travail mécanique tolère un modèle plus léger, le gate reste le garde-fou ; `None` ⇒ moteur par défaut), mint un `session_id`, marque la task `in_progress`, journalise le job (`jobs.record_start`), injecte le MCP de corpus. Bâtit l'argv en `stream-json`/`work=True` ; le runner par défaut (`_make_default_runner`) STREAME le stdout vers `log_path` (suivi live via `dispatch/stream`). Preflight des outils + `trust_workspace` + `which claude` fail-loud AVANT spawn.
Après parse, sur `ok` : `write_decision_doc()` (minerai) → commit du worktree → **clôture `in_progress` → `done`**. Cette dernière transition appartient au PRIMITIVE, pas à la boucle : sans elle, un `forgemaster dispatch` en CLI laissait la task `in_progress`, le reviewer répondait « travail inachevé » et seul un `redrain` sortait de l'impasse — en JETANT le travail déjà payé (constaté le 2026-07-30). L'`UPDATE` est WHERE-gardé, donc idempotent. Sur échec : la task revient `todo` (re-dispatchable). Garde de finalisation : toute exception échappée → `reconcile.mark_job_orphan` (jamais de job zombie) puis re-propage LOUD. Sortie : `{dispatched, reason, task?, job_id?, result?}`.

## write_decision_doc() — persiste le message final du worker en minerai local
`src/forgemaster/dispatch/worker.py:140` · appelé par `dispatch_next()` dans la branche run-réussi uniquement
Écrit le `result` (message final du worker, terminé par `## Décisions prises` par mandat du prompt) **verbatim** dans `<worktree>/docs/decisions/<date_str>--<task_slug>.md`. Provenance portée par le NOM (date+slug) + l'auteur git du commit, pas de frontmatter neuf. **No-op** (retourne `None`) si `result` absent ou blanc : pas de doc vide. Un `preamble` optionnel est **préfixé** au corps — la passe de fix y injecte les findings du gate rouge d'origine (`roadmap.prompt.findings_block`), pour que le minerai capture findings → cause → fix et pas seulement le récit du worker ; la garde no-op reste sur `result` seul, donc un preamble sans corps ne fabrique jamais de minerai. PUR (date injectée → testable sans horloge). Invariant : jamais de minerai orphelin sur un run raté (l'appelant ne l'invoque que si `ok`).

## build_review_prompt() — compose le prompt commission-only du reviewer
`src/forgemaster/dispatch/reviewer.py:57` · appelé par `dispatch_reviewer()`
Assemble le prompt (parti sur stdin) : PERSONA.md + METHOD.md de la facette `review` committées dans le worktree (`_facet_md`), le **mandat commission-only** (un 🔴 ne porte QUE sur une ligne AJOUTÉE citée verbatim et fausse/cassée ; omission = 🟡 max ; doute → 🟡), le **cadrage** Objectif/DoD des tasks (contexte, PAS une checklist de complétude), et le **diff** `dev...branche`. Le mandat porte aussi deux clauses opérationnelles : la **liste close des outils** autorisés pour situer (`Read`/`Grep`/`Glob`, git en lecture, `codemap`/`docsmap`/`frontmap where`) avec l'interdiction explicite d'en appeler d'autres — en headless personne ne peut approuver un prompt, le reviewer resterait bloqué ; et l'obligation de **tenter de réfuter** chaque finding en lisant le code autour, en le jetant s'il ne survit pas. Impose le contrat de sortie : un objet JSON final unique `{"base","findings":[…]}`, chaque finding avec `evidence` citant verbatim une ligne `+` du diff. PUR hors lecture des `.md` de facette.

## _readiness() — gate déterministe « feature prête à reviewer ? »
`src/forgemaster/dispatch/reviewer.py:145` · appelé par `dispatch_reviewer()` avant tout spawn
Retourne `(ok, raison)`. Prête ssi la feature a ≥1 task ET **toutes** ses tasks sont dans un état taskmap **terminal** (`DONE` / `CANCELLED`). L'état vient de `resolver.classify` — la **même autorité de séquencement** que le DAG, donc une seule vérité de « task faite ». C'est plus strict que l'ancien test `todo`/`in_progress`, qui laissait passer un `blocked` : un `BLOCKED`/`BLOCKED_DEPS`/`ERROR`/`CYCLE` n'est pas terminal, donc hold. Aucune heuristique métier : le signal générique de complétude EST la terminalité du statut ; l'ORDRE, lui, reste l'affaire du DAG `depends_on`. Charte : ne pas reviewer un travail inachevé → faux-positifs.

## dispatch_reviewer() — spawn du review-worker Tier-1, verdict SHA-bound
`src/forgemaster/dispatch/reviewer.py:186` · appelé par `cli_dispatch` (route `forgemaster gate review-dispatch <feature>`), auto post-travail
Entrées : `conn`, `settings`, `feature_ref`, `git`/`runner` injectables. Enchaîne les gardes : `_readiness()` (hold si inachevé) → `feature_sha`/`diff_text` (branche absente → hold) → diff vide → hold → `review.status(...).fresh` (verdict déjà frais sur ce HEAD → skip **idempotent**) → worktree vivant. **Chaque refus est journalisé** (`_journal_non_run`) : un non-run laisse une trace, il ne disparaît pas — c'est ce qui rend un « reviewer jamais passé » lisible après coup. Compose le prompt (`build_review_prompt`), injecte le MCP, bâtit l'argv `work=False`/`stream-json` avec l'allowlist read-only **élargie** `REVIEW_TOOLS` (git en lecture + les maps — sans elle le reviewer spinnait sur `Bash`), bascule le worktree sur la facette `review` (`activate_facet` → settings.local.json read-only, sinon la facette de travail resterait active et le reviewer pourrait coder). Preflight + trust + `which claude` fail-loud, puis spawn. Parse via `worker.parse_headless_result`, journalise (`_record_job`, sans toucher au statut des tasks). Si `ok` : `_extract_findings` → `review.write_verdict(sha=head_sha, diff_text=…)` (garde `evidence⊂diff`). **Best-effort** : reviewer échoué → pas de verdict → le gate de merge bloque proprement en aval. Sortie : `{reviewed, reason, verdict?, counts?, rejected?}`.

## Zones non détaillées
- `_result_event` / `_trailing_json_object` (worker.py) : helpers PURS d'extraction de l'objet-résultat depuis un NDJSON stream-json ou un objet unique précédé d'un préambule — le cœur mécanique de `parse_headless_result`.
- `_make_default_runner` (worker.py) : usine du runner par défaut qui streame le stdout vers `log_path` (`run.run_streaming`) ; capture `out_path` sans changer le protocole `Runner`.
- `_default_runner` (reviewer.py) : runner par défaut du reviewer (`run.run`, non streamé — la review est bornée).
- `_counts` (worker.py) : rend le tally des états de tasks pour le message de refus du gate.
- `_facet_md` (reviewer.py) : lit un `.md` de facette (`PERSONA.md`/`METHOD.md`) dans le worktree, `""` si absent.
- `_record_job` (reviewer.py) : journalise le run reviewer dans `dispatch_jobs` (traçabilité + coût), `engine="reviewer-tier1"`, sans faire avancer le DAG.
- `cli_dispatch` (worker.py & reviewer.py) : routes CLI + gate d'auth Claude (jamais de spawn silencieux d'un compte hérité) ; formatage du rapport terminal.
- `_journal_non_run` (reviewer.py) : trace un non-run (readiness, branche absente, diff vide, idempotence) — best-effort, pour qu'un reviewer qui ne passe jamais soit lisible après coup.
- `dispatch_fix` / `make_spin_detector` (worker.py) : la passe de **refix** (re-dispatch d'un worker sur un gate rouge, findings injectés en preamble du minerai) et le prédicat d'abort **non-progression** injecté dans `run_streaming` (`on_line`) — le cœur ne sait pas ce qu'est un « spin », la sémantique appartient au dispatch.
